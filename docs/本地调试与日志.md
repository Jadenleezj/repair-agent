# Postman 本地调试与日志

## 启动与导入

在项目根目录运行：

```bash
source .venv/bin/activate
repair-agent-api
```

也可以打开 `http://127.0.0.1:8000/` 使用聊天工作台输入问题、查看结果并提交审批。

在 Postman 点击 Import，选择 `examples/repair-agent.postman_collection.json`。集合的 `base_url` 默认是 `http://127.0.0.1:8000`。

依次发送健康检查、创建工单、查看工单。创建成功会自动保存 `case_id`。异步执行需要重复查询详情；状态达到 `WAITING_APPROVAL` 后发送人工批准，再查询详情和时间线，确认修复与验收结果。批准会调用配置的修复后端；默认配置为空时使用本地模拟后端。示例 W1001 若已修复，应换未修复的演示订单，或在 Swagger 手动重置演示数据再测试。

## 日志位置

默认相对于启动目录，按上海日期分文件：

```text
logs/
  2026-10-13/
    agent.log    # 全部运行日志（含错误）
    error.log    # ERROR 及以上，包含异常堆栈
    model_responses.log # 模型 API 返回的 JSON（凭据脱敏）
    request_timing.log  # 独立的请求、模型调用与任务耗时
```

每行是一条 JSON，包含时间、级别、模块、线程，及可用的 `request_id`、`case_id`、`order_id`。HTTP 响应的 `X-Request-ID` 可以关联本次请求；后台任务用 `case_id` 关联。阶段开始、结束、耗时、状态，工具查询、模型调用、修复和验收都有日志。模型回退为 WARNING；等待审批是正常暂停。业务审计仍以 timeline 接口为准。

```bash
# 实时查看当天日志
 tail -f "logs/$(date +%F)/agent.log"
# 查询某个工单，包括审批前后
rg 'CASE-实际工单号' logs/
# 只查看异常
cat "logs/$(date +%F)/error.log"
```

在 `.env` 中可选配置：

```dotenv
REPAIR_LOG_DIR=logs
REPAIR_LOG_LEVEL=INFO
```

修改后重启服务生效。跨午夜会自动写入新日期目录；错误文件在首次错误时创建。日志不会自动删除，长期运行时可定期归档旧日期目录。`logs/` 已加入 Git 忽略；配置自定义目录时应另行添加忽略规则。

`agent.log` 不记录完整提示词或模型返回正文。`model_responses.log` 专门保存模型 API 的实际 JSON 返回，包括 `choices[].message.content`、`tool_calls`、`finish_reason` 和 `usage`。返回内容可能包含用户描述或业务数据；环境密钥及响应中的凭据字段会递归脱敏。

## 查看模型实际返回

```bash
tail -f "logs/$(date +%F)/model_responses.log"
rg 'CASE-实际工单号' "logs/$(date +%F)/model_responses.log"
```

每条记录包含 `case_id`、`order_id`（已有时）、`stage`、`adapter`、`model`、`llm_call_id`、`attempt`、`http_status`、服务商的 `model_request_id`（返回该头时）及 `response`。响应在 Pydantic 和工具参数校验之前保存，因此即使随后出现 `LLM ... fallback`，仍可查看模型原本返回的工具名和参数。工具回退日志会记录 `ValueError` 的具体说明。

没有收到可解析的响应时（网络错误、HTTP 错误、超限响应），不会伪造模型正文；查看 `error.log` 和耗时文件中的失败记录。

## 单独记录耗时

```bash
tail -f "logs/$(date +%F)/request_timing.log"
rg 'CASE-实际工单号' "logs/$(date +%F)/request_timing.log"
```

耗时使用单调时钟，单位为 `duration_ms`。同一个文件以 `record_type` 区分：

| 类型 | 测量范围 |
|---|---|
| `http_request` | 用户向本地 API 发起请求，到处理返回；用 `request_id` 关联 |
| `task_run` | Worker 执行一次任务，或同步创建/审批恢复工作流，到本次执行完成或暂停；用 `case_id` 关联 |
| `llm_attempt` | 一次实际模型 HTTP 请求到响应读取结束，失败也记录；包含 HTTP 状态、尝试次数及异常类型 |
| `llm_call` | 一次逻辑模型调用，包含重试、退避和依赖等待；用 `llm_call_id` 关联各次尝试和模型响应 |

异步 `/cases` 的 HTTP 返回不等待模型，所以不能用 `http_request` 耗时代替 `task_run`。暂停后恢复是另一次执行记录；等待用户审批的时间不算作 Worker 执行耗时。`response_received` 仅表示 HTTP JSON 响应已收到，不代表模型输出通过业务校验或修数成功；任务执行函数正常返回也不代表订单已修复。
