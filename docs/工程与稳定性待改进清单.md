# 工程、稳定性与高并发待改进清单

更新日期：2026-10-15。

本文记录待实施的设计和验收要求，不代表功能已经实现，也不代表已经验证生产容量。后续实施时逐项更新状态，并记录测试、压测或演练证据。

## 优先级与当前基线

- P0：接入真实业务写操作前必须补齐的权限、数据一致性与恢复保障。
- P1：进入多人使用、长期运行阶段优先完成的体验、容量和运维工作。
- P2：根据实际规模和评估收益逐步实施的扩展。
- 所有清单项默认状态为「待实施或待验证」。数值目标需根据业务 SLA 和压测结果确定，不使用未经验证的容量承诺。

当前已有持久化有界队列、有限 Worker、租约与心跳、LangGraph 检查点、审批暂停恢复、任务与模型预算、协作式取消、只读有限重试、依赖并发隔离与熔断、写前意图、结果未知只读对账、后端幂等与版本契约、独立验收、大证据归档和终态保留期清理。这些机制应继续保留和验证，不能列为完全缺失。

当前默认是单机 SQLite 与进程内线程 Worker；平台工具含模拟数据；默认修复后端为本地 HTTP MockTransport，支持配置独立后端；指标为进程内 JSON 指标。历史 RAG 使用 BM25，没有向量检索和 rerank。基础故障测试不等于真实生产环境长期稳定性验证。

## 1. 用户反馈、进度事件与 SSE

| 编号 | 优先级 | 当前情况与待改进项 | 验收标准 |
|---|---|---|---|
| UX-01 | P1 | 提交持久化成功后明确显示「问题已提交，正在等待处理」，区分排队、执行、审批、结果未知和完成；仅在确实可估算时显示等待时间 | 文案与后端状态一致；202 不显示为修复成功；提交超时引导核对已有工单 |
| UX-02 | P1 | 建立结构化进度事件，分别表达「已核实什么、正在做什么、接下来准备做什么」 | 阶段事件包含 event_id、case_id、阶段、时间、已确认事实摘要、实际 next_action；没有查到证据前不宣布已确认；未知下一步不编造计划 |
| UX-03 | P1 | 根据图节点和工具结果生成进度文案，普通阶段优先模板，解释性结论按需使用模型 | 进度生成不阻塞修复主流程；不把原始日志、内部推理、密钥或其他用户数据直接展示；能区分接口执行成功和验收成功 |
| UX-04 | P1 | 增加 SSE 事件接口，前端订阅并追加进度，普通 POST 仍负责提交与审批 | 使用 text/event-stream；正确分帧；连接建立时可同步当前快照；终态发送结论；断线不会取消后台任务 |
| UX-05 | P1 | 持久化事件并支持断线补发、去重与终态恢复 | event_id 可按工单有序恢复；依据 Last-Event-ID 或显式游标补发；前端按 ID 去重；过期游标返回快照并标明补发边界；跨重启可恢复 |
| UX-06 | P1 | 配置 SSE 心跳、代理缓冲、空闲超时、连接额度和断线降级 | 实际部署代理下能及时收到事件；断网/重连/多标签页/慢客户端可验证；慢客户端缓冲有上限；SSE 失败可退回低频查询；连接有工单访问授权 |
| UX-07 | P1 | 完善最终结论，包含发现、执行方案、审批情况、验收结果和后续动作 | 成功、证据不足、拒绝、失败、结果未知均有明确结论；结果未知不宣称成功或撤销；引用可追溯 |

建议事件链路：Worker 执行节点 → 持久化阶段事件 → 通知事件消费者 → SSE 推送 → 前端展示。订阅连接不持有任务执行权。多实例下需要共享事件存储及通知机制，进程内队列不足以跨实例传递事件。若 SSE 服务仍高频查询数据库，必须测量其读负载，不能认为增加 SSE 就消除了轮询成本。

## 2. API、高并发和容量控制

当前前端每轮并行查询工单详情和任务状态，成功后等待 1.5 秒再查；错误退避最长 8 秒。可见页面每 10 秒刷新列表和就绪状态；选中任务的轮询尚未因页面隐藏而暂停。忽略响应耗时，1,000 个活跃任务查看页面的进度查询约为 1,333 QPS，属于估算而非压测结果。

| 编号 | 优先级 | 待改进项 | 验收标准 |
|---|---|---|---|
| API-01 | P1 | 提供轻量进度快照接口，避免每轮传完整证据和审计；详情按需加载 | 状态、阶段、更新时间及版本可独立查询；对比优化前后的响应体、数据库读取和 P95 延迟 |
| API-02 | P1 | 轮询按阶段调整间隔，加入随机抖动；隐藏页面暂停，恢复可见时立即同步 | 排队、运行、审批、终态分别验证；无重复定时器；旧请求不覆盖新工单；轮询错误不重新提交任务 |
| API-03 | P1 | 支持状态版本或 ETag，按授权范围使用短缓存，列表分页和轻量摘要 | 状态变更后按设计时限刷新；租户之间不共享受限数据；缓存失效与版本更新可验证 |
| API-04 | P0 | 增加创建工单的请求幂等键，应对用户连点和提交响应丢失 | 相同键和相同请求返回原工单；相同键但不同内容拒绝；并发提交不会创建重复工单；键有作用域和保留期 |
| API-05 | P1 | 增加用户、租户和端点级限流、配额及队列背压反馈 | 超限明确返回状态与重试建议；公平调度防止单租户占满队列；队列满仍不创建孤立工单 |
| CAP-01 | P1 | 建立容量模型，分别估算 API 读请求、任务吞吐、模型额度、后端额度和 SSE 连接数 | 报告区分提交吞吐与完成吞吐，记录平均/P95 任务时长、等待时间、最老任务、内存和依赖瓶颈 |
| CAP-02 | P1 | 大规模前评估迁移 PostgreSQL、连接池和索引，不直接依赖共享盘上的 SQLite | 保持提交、领取、审批和写意图的原子性；并发迁移测试；查询执行计划及连接上限可检查 |
| CAP-03 | P2 | 分离 API 与 Worker 部署；按积压和依赖额度扩缩容 | 扩缩容不重复写；有停机排空；多实例的租约、事件、指标和配额协调可验证 |
| CAP-04 | P1 | 将当前进程内依赖并发额度扩展为多实例全局预算或明确分配额度 | 多实例总调用不超过服务商限制；429 风暴有退避；线程、连接池与消费者数不盲目增加 |
| CAP-05 | P1 | 区分长短任务，检查饥饿和队头阻塞，按业务需要设计优先级 | 低优先级有等待上界或明确策略；高优先级不能绕过审批与安全门禁；积压可观测 |

## 3. 修复一致性、幂等与权限

| 编号 | 优先级 | 当前情况与待改进项 | 验收标准 |
|---|---|---|---|
| SAFE-01 | P0 | 接入真实身份、RBAC 与租户隔离，替换请求中自行填写的身份；覆盖查询、审批、事件、知识和归档接口 | 无权限用户不能读取或审批其他工单；审批者身份来自可信认证；SSE 与重连同样授权；审批权限由服务端判断 |
| SAFE-02 | P0 | 审批绑定明确的方案版本、订单版本和证据快照，增加有效期；必要时实行提交与审批职责分离 | 审批过期或方案/关键证据变化后重新确认；旧审批不能授权新计划；并发审批维持一次有效决策 |
| SAFE-03 | P0 | 执行前从订单版本校验扩展为必要业务前提复核；写入时在业务后端事务内再次校验 | 模拟签收记录、派送任务或订单在等待期变化，修复被阻止；后端条件检查与写入原子完成 |
| SAFE-04 | P0 | 验证真实后端的幂等实现：执行记录、请求绑定和业务写入事务一致 | 同键同请求不重复修改；同键不同参数拒绝；提交成功后响应丢失可对账；幂等记录保留期覆盖恢复与审计窗口 |
| SAFE-05 | P0 | 防止同一订单不同工单并发修复；目前 case_id + Playbook ID 只覆盖同一次操作 | 使用业务状态条件、乐观锁及必要的订单级互斥；并发工单只有合法操作成功；若使用租约锁，后端需拒绝失效执行者，不能只依赖锁 |
| SAFE-06 | P0 | 完善真实后端结果未知对账契约和人工处置流程，保留不自动重发写的原则 | 注入提交后超时、执行记录暂不可见、后端不可用；均不重复发送修复；可追溯查询、升级和人工结论 |
| SAFE-07 | P1 | 方案与接口契约版本化，定义回滚或补偿能力、不可逆操作边界 | 旧工单不会静默执行新方案；回滚有单独授权及前提；补偿不等于再次调用原写接口 |

## 4. 长期运行与故障恢复

| 编号 | 优先级 | 待改进项 | 验收标准 |
|---|---|---|---|
| REL-01 | P1 | 在真实延迟和错误率下开展至少 24 小时持续运行及资源泄漏检查 | 记录连接、线程、内存、数据库体积、错误率和队列等待趋势；明确负载、环境和通过阈值 |
| REL-02 | P0 | 扩展故障注入，覆盖写前/写后进程退出、租约失效、重复恢复及数据库不可用 | 旧 Worker 不覆盖新状态；读阶段可恢复；可能已写阶段仅对账；工单、队列和检查点状态可核对 |
| REL-03 | P1 | 对无法保证超时退出的外部工具增加进程隔离和强制终止策略 | 挂死工具不会长期耗尽 Worker；终止后正确区分未写与结果未知；不声称线程取消可以强杀阻塞调用 |
| REL-04 | P1 | 校验重试预算、剩余时间传播、熔断和故障恢复策略 | 不叠加多层无限重试；无效参数/无权限不重试；恢复时避免集中重试；所有调用受任务剩余预算限制 |
| REL-05 | P1 | 验证优雅停机和滚动发布，隔离数据库迁移与运行中的旧版本 | 停止领取后有界收尾；超期任务交接可恢复；写操作不重复；不让不兼容版本同时修改已迁移数据 |
| REL-06 | P0 | 制定数据库、检查点、审计和归档的备份恢复方案 | 实际执行恢复演练；记录 RPO/RTO；恢复后未决写操作与后端执行记录核对；不能仅确认备份文件存在 |
| REL-07 | P1 | 明确保留、删除与容量报警策略，覆盖同步 CLI、知识、SSE 事件和归档 | 待审批/结果未知任务不被误删；幂等记录不提前删除；引用仍可访问；磁盘不足有明确降级和报警 |

## 6. 模型、Playbook 与 RAG

| 编号 | 优先级 | 当前情况与待改进项 | 验收标准 |
|---|---|---|---|
| AI-01 | P1 | 当前诊断仅收到 Playbook ID 列表；补充名称、适用前提、排除条件、必要证据及方案版本 | 正确选择经审核方案；证据不足返回无方案；地址仍由代码映射；提示内容不替代后端校验 |
| AI-02 | P1 | 审计五维评分的来源，替换或标明固定历史匹配值及配置成功率，按真实评估校准阈值 | 不把 BM25 分数或模型自评当正确概率；分项有来源和样本定义；硬门禁持续生效；分 Playbook 评估 |
| AI-03 | P1 | 构建独立模型评估集，包含误报、缺证据、冲突、未知类型、非法工具和提示注入 | 衡量诊断、工具选择、方案选择、证据引用和错误执行；模型/提示/方案升级可回归 |
| AI-04 | P1 | 将历史经验接入调查规划，并在实时调查后按状态和错误码二次检索 | 与原流程对比调查次数、诊断质量、成本和错误推荐；历史仍不替代当前事实 |
| RAG-01 | P1 | 导入已验收且经审核脱敏的真实案例，加入版本、权限、时效和撤回机制 | 案例可追溯；不自动把模型猜测入库；过期方案不被推荐；跨租户隔离 |
| RAG-02 | P1 | 记录脱敏 query 和检索结果，建设 Recall@K、MRR、nDCG 与无答案评估 | 使用未入库的独立问题；统计高频失败查询；区分检索错误与生成错误；标注和指标可复现 |
| RAG-03 | P2 | 规模与措辞多样性增加时试验语义切分、embedding、混合召回、RRF 与 rerank | 先比较 BM25 基线，做消融实验；记录收益、延迟和成本；候选集扩大不绕过权限；模型版本变更可重建索引 |
| AI-05 | P2 | 复杂多系统任务再考虑显式 Plan-Execute，当前仍是下一工具决策循环 | 多步计划可校验、持久化、跟踪依赖和重规划；禁止生成任意写操作；仅在评估有收益后采用 |

## 建议实施顺序

1. 演示体验：UX-01～03、07 与 API-01～02，先定义可靠阶段事件，再接 SSE。
2. 真实业务接入：SAFE-01～06、API-04、REL-02、06，补齐身份、审批绑定、事务幂等与恢复演练。
3. 多人长期使用：UX-04～06、观测、持续运行和压测，根据结果选择数据库迁移与部署拆分。
4. 知识与模型提升：先补真实知识与独立评估，再做混合检索或显式计划，避免仅为增加技术组件而扩展。

这不是严格串行的排期。真实写操作上线前必须先完成相关 P0 项；数据库和部署升级应由实际容量结果驱动。
