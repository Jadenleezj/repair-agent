# RepairPilot 稳定性与长期运行

## 已实现的运行模型

默认 HTTP 接口采用持久化队列：

```text
POST /cases → 工单与任务原子入库 → HTTP 202 返回 case_id
                                        ↓
                              有限数量的后台 Worker
                                        ↓
              检索 → 只读调查 → 诊断 → 门禁 → 修复接口 → 验收
                                        ↓
                  等待审批 / 完成 / 失败 / 结果未知进入对账
```

审批时保存 LangGraph 检查点并释放 Worker 槽位。批准或拒绝会重新入队，由 Worker 恢复检查点。

`wait=true` 保留旧版同步演示入口，CLI 仍同步运行。不要在异步工单的审批接口上使用 `wait=true`。生产型常驻服务应使用默认队列模式。

## 启动和使用

```bash
cd repair-agent
source .venv/bin/activate
repair-agent-api
```

启动会运行消费者、心跳和维护线程，关闭服务时执行有界收尾。

```bash
# 立即返回工单 ID，状态为 QUEUED
curl -X POST http://127.0.0.1:8000/cases \
  -H 'Content-Type: application/json' \
  -d '{"message":"运单 W1001 已签收但仍在派送中"}'

# 将 CASE_ID 替换为返回的编号
curl http://127.0.0.1:8000/cases/CASE_ID
curl http://127.0.0.1:8000/cases/CASE_ID/task

# 到 WAITING_APPROVAL 后提交审批，随后查询工单是否 SUCCEEDED
curl -X POST http://127.0.0.1:8000/cases/CASE_ID/approval \
  -H 'Content-Type: application/json' \
  -d '{"approved":true,"actor_id":"developer","comment":"已核实"}'
```

队列满返回 429，不创建孤立工单。两个并发审批最多接受一个。不同 Worker 使用独立数据库和 HTTP 连接，不再以一把全局图锁串行所有异步工单。

## 任务领取与恢复

`repair_jobs` 保存任务类型、状态、尝试次数、可执行时间、执行阶段、取消标志、租约和心跳。SQLite 的 `BEGIN IMMEDIATE` 保证领取和状态变更原子化。

每次领取产生新的 owner 令牌。旧 Worker 的心跳、写前意图和最终状态回写必须通过 owner 与租约检查；节点前后也检查执行权。

- **读阶段租约过期**：有限重试，从已有检查点恢复。
- **写请求可能已发出**：只进入 RECONCILE，不重新调用修复接口。
- **等待审批**：没有活跃租约，不占执行槽位。
- **达到恢复次数上限**：任务失败或进入 MANUAL_REVIEW，需要人工处理。

多进程可以共享同一个本地 SQLite 文件领取任务；此版本适用于单机有限并发。不要把 SQLite 文件放到网络共享盘作为多节点生产队列。更大规模部署应替换为具备事务与原子领取能力的数据库。

## 任务预算与取消

预算包括总任务时长、推理入口次数、真实模型请求次数（含重试）、token 用量，以及重复工具与参数的调用次数。单次网络超时会收紧到任务剩余时间。

模型使用量优先依据返回的 usage；输入按完整请求的 UTF-8 字节数保守预留，包括 JSON Schema，没有 usage 时输出也按字节估算。请求携带 `max_tokens` 限制剩余输出额度，兼容的模型服务需遵守该参数。输入预留可能明显高于实际 token，因此预算不是计费精确值。默认规则推理不消耗真实模型 token。

```bash
curl -X POST http://127.0.0.1:8000/cases/CASE_ID/cancel
```

待执行和待审批任务可以立即取消；执行中的读任务在检查点边界响应取消。写意图已经保存的任务不能被接口宣称撤销，需要先核实执行结果。

Python 线程不会被强行杀死。底层 HTTP 超时、节点前后检查和租约撤销共同防止慢任务继续推进。自定义工具若使用无超时阻塞调用，仍可能占用一个线程；需要强制终止的第三方工具应使用独立进程隔离。总时限是协作式预算，不是操作系统级硬实时保证。

## 修复结果未知与对账

写前先持久化 case、运单、Playbook 与诊断版本，再发送固定后端接口请求。超时或响应不可解析时使用 EXECUTION_OUTCOME_UNKNOWN。

对账 Worker 只做：

1. 按原幂等键调用 `GET /repair-executions?idempotency_key=...`。
2. 校验返回记录对应当前工单和修复方案。
3. 后端确认成功后，独立读取当前业务数据验收。
4. 后端确认失败则结束；记录暂未找到或接口不可用则有限再查。

查询不到执行记录不能证明“未执行”，因此不会自动重发修复。超过次数上限后保持结果未知，任务进入 MANUAL_REVIEW。核实后端恢复后可人工触发再次只读对账：

```bash
curl -X POST http://127.0.0.1:8000/cases/CASE_ID/reconcile
```

生产修复后端需实现执行记录查询契约，以及真正的幂等和状态版本检查。Agent 的重试和租约不能替代后端业务幂等。

## 平台隔离与重试

平台和 LLM 使用独立并发额度与熔断状态。只读 HTTP 的网络错误、429 与部分 5xx 可以有限重试，退避加入抖动；参数、权限、数据不存在等情况不盲目重试。

写接口没有自动重试。日志、配置中心、任务平台和 Hive 当前仍为本地模拟；真实接入适配器也必须设置底层超时。错误按查询不可用、无数据和未授权区分，LLM 回退规则会记录日志和指标。

## 工具结果与数据保留

每条证据超过输出预算时，将完整 JSON 写入 `<业务数据库>.artifacts/`，图状态只保留内容哈希、预览和查询收窄提示。

远端响应另有流式接收上限：只读和模型响应最多为输出预算的 8 倍，修复响应最多 256 KB。超过接收上限时立即关闭响应流，返回不可用或未知执行结果，不会把超限原文完整下载后再归档。

为了避免自动修复使用不完整证据，超大结果被标记为 UNAVAILABLE，不能截断后仍冒充完整事实。历史引用过大也会归档，诊断继续使用当前业务证据。

`GET /artifacts/{哈希}` 可检查原始结果。接口仅用于本地演示，真实部署应加入身份与访问控制。

维护线程定期清理超过保留期的已终结异步工单、时间线、审批记录与 LangGraph 检查点。等待审批、未决修复和人工对账任务不清理。未被剩余工单引用的过期归档也会删除。

后端执行幂等记录不随 Agent 工单清理；其保留策略应与重试窗口和审计要求一致。历史知识库也不自动清理。同步 CLI 工单未进入任务表，不在本轮任务清理范围内。

## 监控接口

| 接口 | 含义 |
|---|---|
| GET /health | 进程存活检查 |
| GET /ready | 数据库可用、Worker 与心跳线程运行、未进入停机 |
| GET /metrics | JSON 格式队列、累计计数、阶段耗时与依赖熔断状态 |
| GET /cases/{id}/task | 任务种类、状态、尝试次数、租约和取消情况 |

阶段耗时保存 count、sum、max，不保留无限样本。计数标签使用固定阶段或工具名，不使用 case_id。指标目前为进程内累计值，重启后归零；它不是 Prometheus exporter，队列状态来自持久化数据库。

建议关注队列最老等待时间、任务错误和超时、未决写操作、平台错误与重试、熔断、LLM 回退和模型调用次数。外部平台故障不会直接令整个服务的 readiness 失败，避免一个非必要依赖让所有请求无法进入队列。

## 配置

环境变量以 `REPAIR_` 开头，启动时校验。以下是主要默认值：

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| REPAIR_WORKERS | 2 | 工作线程数 |
| REPAIR_QUEUE_CAPACITY | 100 | 待执行与执行中任务总上限 |
| REPAIR_TASK_SECONDS | 120 | 单次领取的任务预算 |
| REPAIR_LEASE_SECONDS | 30 | 租约有效时间 |
| REPAIR_HEARTBEAT_SECONDS | 5 | 续租间隔，租约至少为其三倍 |
| REPAIR_MAX_ATTEMPTS | 3 | 恢复或对账尝试上限 |
| REPAIR_MODEL_CALLS | 30 | 推理入口及真实模型请求各自上限 |
| REPAIR_TOKEN_BUDGET | 30000 | 单任务保守 token 预算 |
| REPAIR_REPEAT_LIMIT | 2 | 相同调查工具与参数重复上限 |
| REPAIR_TOOL_TIMEOUT_SECONDS | 10 | 工具 HTTP 超时与容量等待上限 |
| REPAIR_MODEL_TIMEOUT_SECONDS | 20 | 模型请求超时 |
| REPAIR_READ_RETRIES | 2 | 首次调用之外允许的只读重试次数 |
| REPAIR_RETRY_BASE_SECONDS | 0.2 | 重试退避基数，按尝试次数指数增长并加入抖动 |
| REPAIR_POLL_SECONDS | 0.2 | 消费者空闲轮询间隔 |
| REPAIR_TOOL_CONCURRENCY | 2 | 每依赖并发上限 |
| REPAIR_BREAKER_FAILURES | 3 | 连续失败熔断阈值 |
| REPAIR_BREAKER_SECONDS | 30 | 熔断冷却时间 |
| REPAIR_OUTPUT_BYTES | 32000 | 单条证据或历史引用输出上限 |
| REPAIR_SHUTDOWN_SECONDS | 5 | 停机收尾等待时间 |
| REPAIR_RETENTION_DAYS | 30 | 已终结异步工单保留时间 |
| REPAIR_MAINTENANCE_SECONDS | 60 | 清理检查间隔 |

## 代码入口

- `jobs.py`：持久化队列、原子领取、租约、审批和回收。
- `worker.py`：后台消费、心跳、任务预算、停机和对账调度。
- `reliability.py`：预算、取消、容量隔离、熔断、退避及指标。
- `artifacts.py`：输出归档、哈希引用及清理。
- `backend_client.py`、`backend_api.py`：修复结果查询契约。
- `http_io.py`：有界流式读取 JSON 响应与资源释放。
- `runtime.py`、`api.py`：连接现有图、API 和生命周期。

## 已验证范围

测试包含队列满拒绝、持久化后重启消费、审批恢复、旧租约回写拒绝、写阶段恢复只对账、任务预算、运行中取消、只读重试与熔断、超大结果归档、停机撤销执行权和过期清理。还包含多个工单连续消费，以及后端提交成功但响应丢失时只对账、不重复写入。

这些是本地故障注入与短时连续运行检查，尚未进行真实平台上的 24 小时持续运行。上线前需要在真实接口延迟、错误率、数据库容量和部署停机条件下验证，并补齐认证与权限控制。
