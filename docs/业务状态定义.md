# 订单与 Delivery Task 状态定义

统一定义在 `repair_agent/domain/statuses.py`。数据库和接口使用大写代码，页面名称采用下面的英文写法。

## 订单 Order

| 代码 | 显示名称 | 含义 |
|---|---|---|
| CREATE | Create | 订单刚刚创建 |
| DELIVERING | Delivering | 骑手已经接单 |
| ON_HOLD | On Hold | 因某些原因暂时搁置派送 |
| DELIVERED | Delivered | 订单派送完成 |
| RETURNED | Returned | 异常情况导致无法派送 |

## 派送任务 Delivery Task

英文为 **Delivery Task**，类名通常写 `DeliveryTask`。不需要重复 Task。

| 代码 | 显示名称 | 含义 |
|---|---|---|
| CREATE | Create | 刚创建派送任务 |
| PENDING_ASSIGN | Pending Assign | 已有订单加入，等待骑手接任务 |
| ASSIGNED | Assigned | 骑手已经接派送任务 |
| COMPLETE | Complete | 任务内所有订单均已 Delivered |

`Delivered` 属于订单，`Complete` 属于派送任务。一张订单 Delivered、同一任务内其他订单尚未完成时，任务仍为 Assigned，是正常情况。

Returned 表示无法派送，当前不计为 Delivered；On Hold 也不计为派送完成。如果业务后续允许 Returned 参与任务完结，需要另行明确完结条件。

## 查询与修改位置

- `domain/statuses.py:OrderStatus/DeliveryTaskStatus`：合法状态代码。
- `domain/statuses.py:ORDER_DESCRIPTIONS/TASK_DESCRIPTIONS`：名称与含义。
- `persistence/repository.py:seed_demo_data`：默认模拟状态。
- `agent/reasoning.py:RuleReasoner.diagnose`：根据状态和作业证据提出诊断。
- `demo/backend.py:execute_playbook`：模拟业务接口的事务前提与状态更新。
- `domain/statuses.py:verify_business_state`：修复后的状态验收。
- `tools/fixtures/platforms.json`：日志、配置、任务平台和 Hive 的模拟快照。

`GET /statuses` 可查看两类业务状态。Agent 工单的 CREATED、QUEUED、WAITING_APPROVAL、SUCCEEDED 等是执行过程状态，仍在工作流和队列中使用，不属于订单或 Delivery Task。

## 已实现的规则

接单状态同步依据 `TASK_ACCEPTED` 作业记录，将仍为 CREATE 的订单补齐为 DELIVERING，要求任务为 ASSIGNED。已有 `PICKUP_SCAN_NOT_APPLIED`、`APPLY_PICKUP_SCAN_V1` 和 `/repairs/pickup-scan` 暂时保留为兼容标识；含义已调整为接单状态同步，界面说明采用新业务含义。

签收状态同步要求订单为 DELIVERING、任务为 ASSIGNED 或 COMPLETE，并有成功的签收记录。不会将 ON_HOLD 或 RETURNED 自动转成 Delivered。

模拟任务快照通过 `task_id` 表示多订单归属，同一任务的各行保存相同任务状态。查询返回 `member_order_ids` 和 `all_orders_delivered`。封装修复接口更新单张订单后，检查全部成员，只有都 Delivered 才将任务设为 COMPLETE；否则保留 ASSIGNED。实际生产中应由真实 Delivery Task 服务提供权威成员关系、聚合状态、并发控制和同等事务保证。

目前没有新增 On Hold、Returned 的自动修复方案，也没有通用业务状态编辑接口。

## 旧演示数据库兼容

启动 Repository 时为任务快照补充 `task_id`，迁移旧演示状态：订单 CREATED/ASSIGNED → CREATE，PICKED_UP → DELIVERING；任务 DELIVERING → ASSIGNED、DELIVERED → COMPLETE、CREATED → CREATE。旧模拟 PICKUP_SCAN 记录转换为 TASK_ACCEPTED。

这些迁移只作用于本地演示业务表，不修改真实后端、不清空工单与审批、也不重写历史检查点或知识库。历史示例和引用描述需要按新业务含义整理。
