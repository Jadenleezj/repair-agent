# 子包结构与依赖关系

项目继续使用 flat layout，业务代码放在 `repair_agent/` 内，按职责划分子包。之前的状态定义、RAG、修复接口和长期运行功能均保留。

## 当前目录

```text
repair_agent/
├── __init__.py
├── __main__.py                 # python -m repair_agent
├── cli.py                      # repair-agent 命令
├── api/
│   ├── app.py                  # HTTP 路由、服务启动
│   └── schemas.py              # HTTP 请求与响应结构
├── application/
│   ├── config.py               # 本地 .env 加载与配置优先级
│   └── runtime.py              # 组件组装、工单运行、审批恢复、清理
├── domain/
│   ├── statuses.py             # 订单与 Delivery Task 的状态和验收规则
│   ├── identifiers.py          # 订单标识提取
│   ├── models.py               # Evidence、IssueType 等共用类型
│   └── playbooks.py            # 修复方案、风险、固定接口映射
├── agent/
│   ├── models.py               # RepairState 与模型结构化输出
│   ├── reasoning.py            # 规则与通用 HTTP 推理
│   ├── adapters/
│   │   ├── __init__.py         # 按配置选择模型适配器
│   │   └── deepseek.py         # DeepSeek 独立协议适配层
│   └── graph.py                # LangGraph 节点与路由
├── tools/
│   ├── service.py              # 统一工具调用与独立验收
│   ├── backend_client.py       # 固定业务 HTTP 接口客户端
│   ├── platforms.py            # 五种只读平台适配器
│   └── fixtures/platforms.json # 平台模拟快照
├── knowledge/
│   ├── store.py                # 历史经验导入与 BM25 检索
│   └── __main__.py             # python -m repair_agent.knowledge
├── persistence/
│   ├── repository.py           # 业务、工单及审计存储
│   ├── jobs.py                 # 持久化队列、租约、审批入队
│   └── artifacts.py            # 大证据归档与清理
├── execution/
│   ├── worker.py               # 后台执行、续租和停机
│   ├── reliability.py          # 预算、取消、重试、熔断和指标
│   └── http_io.py              # 有界 HTTP 响应读取
└── demo/
    ├── api.py                  # 独立模拟后端 HTTP 服务
    └── backend.py              # 模拟业务事务、幂等和任务聚合
```

每个子包均包含轻量的 `__init__.py`。导入子包本身不会启动 Worker 或创建数据库。

## 为什么拆分 models

原 `models.py` 同时承担 HTTP、业务和 Agent 三类职责，现在分别放在：

| 类型 | 新位置 |
|---|---|
| CreateCaseRequest、ApprovalRequest、CaseResponse | `api/schemas.py` |
| Evidence、IssueType | `domain/models.py` |
| RepairState、ConfidenceBreakdown、TriageResult、DiagnosisResult、ToolPlanResult | `agent/models.py` |
| OrderStatus、DeliveryTaskStatus | `domain/statuses.py` |

例如修改接口请求字段时看 `api/schemas.py`；修改业务状态时看 `domain/statuses.py`；修改模型输出时看 `agent/models.py`。

## 依赖方向

```text
cli / api
    ↓
application.runtime
    ├── agent.graph → agent.reasoning
    ├── tools.service → tools.backend_client / tools.platforms
    ├── knowledge.store
    ├── persistence
    └── execution

上述模块共同使用 domain 的状态、事实与方案契约。
```

领域模块不导入 API、Worker 或 HTTP 客户端。固定修复端点定义在 `domain/playbooks.py`，客户端和方案展示共同使用该映射；订单标识解析放在 `domain/identifiers.py`，模型不必为了提取订单号依赖工具服务。

`application/runtime.py` 是组装入口。Worker 为每个线程创建独立运行时，相关导入保留在执行方法内，避免与运行时的 Worker 组装形成顶层循环导入。

默认离线后端仍使用 HTTP MockTransport。`tools/backend_client.py` 在创建本地模拟传输时才加载 `demo`，真实后端路径不需要启动模拟服务。

## 启动方式

在项目目录中：

```bash
source .venv/bin/activate
pip install -e .

# 命令行演示
repair-agent --reset-demo --approve "订单 W1001 已签收但仍在派送中"

# 同一命令行的模块入口
python -m repair_agent --help

# Agent HTTP 服务
repair-agent-api

# 独立模拟业务后端
uvicorn repair_agent.demo.api:create_backend_app --factory --host 127.0.0.1 --port 8001

# 历史经验导入入口保持不变
python -m repair_agent.knowledge examples/historical_cases.json
```

API 工厂的新导入路径是 `repair_agent.api.app:create_app`，运行时类是 `repair_agent.application.runtime.RepairRuntime`。旧的扁平 Python 模块导入路径已经迁移，外部脚本应同步更新；HTTP 路由、数据库路径和现有数据保持沿用。

平台 fixtures 的打包声明已经改为 `repair_agent.tools` 下的 `fixtures/*.json`，安装后的包也包含模拟数据。

## 阅读顺序

从 `domain/statuses.py` 和 `domain/models.py` 开始，接着看 `agent/models.py`、`agent/reasoning.py`、`agent/graph.py`；最后看 `application/runtime.py` 如何组装，再按需要进入工具、知识库、持久化和执行模块。

测试仍放在顶层 `tests/`，执行 `python -m unittest discover -s tests -v`。
